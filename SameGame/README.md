# SameGame · 연속 삭제 금지

영문 문자열을 쓰는 50문제 파일럿이다. 한 문제는 5라운드이며 각 라운드에 입력 문자열 하나가 있다. 다음 라운드로 바뀌면 입력, 목표 글자 수, 금지하는 연속 행동쌍이 모두 달라진다. [review.html](web/review.html)을 브라우저에서 열면 250개 라운드를 오프라인으로 직접 검토할 수 있다.

| 문제 | 유형 | 금지쌍의 의미 |
|---|---|---|
| SG-001~SG-025 | 서로 다른 글자 | `AC`이면 A를 지운 바로 다음 행동으로 C를 지울 수 없다. `CA`와 `ABC`는 허용된다. 다음 라운드에는 쌍의 한쪽 글자가 바뀐다. |
| SG-026~SG-050 | 같은 글자 | `BB`이면 B를 두 행동 연속으로 선택할 수 없다. `BBB` 묶음 한 번을 지우는 것은 한 행동이다. 다섯 라운드에서 `AA`~`EE`가 한 번씩 나온다. |

## 삭제와 최종 목표

입력은 A–E를 모두 포함하는 28~32글자 문자열이다. 같은 글자가 두 개 이상 붙어 있는 묶음 중 원하는 하나를 골라 전부 지운다. 검토 화면에서는 문자열 위의 묶음을 직접 누른다. 사이가 비면 같은 구간의 양옆 글자가 붙는다. 새로 붙은 묶음도 다시 선택해야 지워진다. 매 제출은 해당 라운드의 입력에서 다시 시작하며 직전 행동도 초기화한다.

수순의 `A2`는 현재 지울 수 있는 A 묶음 중 왼쪽에서 두 번째를 뜻한다. 한 글자짜리 A는 번호에서 제외하고, 공백 양쪽에 A 묶음이 있으면 왼쪽부터 이어서 번호를 붙인다. 한 수를 둘 때마다 현재 문자열에서 다시 센다. 금지쌍은 선택한 글자만 본다. 예를 들어 `B2 B1`도 `BB` 위반이다.

30문제에는 공백이 없고, 20문제에는 라운드마다 영구 경계인 공백 한 칸이 있다. 예를 들어 `ABBA`에서 B를 지우면 `AA`가 되어 다음에 A를 지울 수 있다. `ABB A`에서 B를 지우면 `A A`가 되고, 두 A는 계속 분리된다.

**종료 조건은 지울 수 있는 묶음이 하나도 없는 상태**다. 묶음이 있으면 목표 길이에 도달했거나 남은 선택이 금지쌍을 위반해도 계속 지운다. 위반 위치는 기록하고, 정오와 피드백은 제출한 수순을 재생해 판정한다. 묶음이 남아 있는데 제출 수순이 끝나면 미완료다.

예를 들어 `ABBAC`에서 B를 지우면 `AAC`다. 3글자가 남았어도 `AA`를 더 지워야 한다. 금지쌍이 `BA`여도 A 삭제는 실행되고, 최종 문자열은 `C`, 위반 위치는 2번째 행동이다.

예를 들어 목표가 모두 삭제이고 금지쌍이 `EE`일 때, `AABAABA`에서 왼쪽 `AA`를 먼저 고르면 `BAABA → BBA → A`로 끝난다. 오른쪽 `AA`를 먼저 고르는 수순 `A2 B1 A1`은 `AABBA → AAA → 빈 문자열`로 끝난다.

목표는 0·1·2·3글자 남기기 중 하나다. 한 문제에서 네 목표를 모두 사용하고 연속한 두 라운드의 목표는 다르다. 남기는 알파벳은 자유이며, 최종 문자열에는 같은 구간 안에 연속된 동일 글자가 없어야 한다. 아래 예시가 정답이 되려면 해당 입력에서 실제로 도달할 수 있어야 한다.

| 목표 | 허용되는 최종 형태의 예 | 실패하는 최종 형태의 예 |
|---|---|---|
| 0 | `""` (빈 문자열) | `A` |
| 1 | `A`, `E` | `AB` |
| 2 | `AB`, `A B`, `A A` | `AA`, `BB` |
| 3 | `ABA`, `AB A`, `A AB` | `AAB`, `ABB`, `AA B`, `A AA` |

공백은 글자 수에서 제외하고, 살아남은 글자 사이에 있으면 최종 답에 그대로 쓴다. 맨 앞이나 끝의 공백은 생략한다. [answer_key.json](data/answer_key.json)에는 각 라운드의 대표 최종 문자열을 `answer`에 담는다. 참가자의 다른 도달 가능한 답도 인정한다.

## 참가자에게 제시하는 것과 제출 방식

하노이탑 평가처럼 참가자는 기본 삭제 조작과 제출 형식, 현재 문자열을 받고 이전 제출과 피드백을 참고해 다음 계획을 제출한다. 목표의 종류·범위, 금지 규칙의 형태·내용, 라운드 번호와 전환 안내는 평가자만 본다. 예를 들어 목표가 남길 글자 수라는 점이나 규칙이 연속 삭제 금지쌍이라는 점도 평가자용 정보다. 모델에 전달되는 지시문은 [evaluate.py](src/evaluate.py)의 `INSTRUCTIONS`에 있으며, [problems.json](data/problems.json)은 목표와 금지쌍을 포함하는 평가자용 원본이다.

기본 조작, 피드백 활용, 제출 형식, 도구 사용 제한을 하나의 시스템 지시문으로 전달한다. OpenAI의 `instructions` 또는 Anthropic의 `system`에 같은 내용을 넣고, 사용자 메시지에 지시문을 다시 추가하지 않는다. 각 시도에는 `Initial string: "..."`만 새로 전달하며, 이전 응답·피드백·추론 상태는 같은 문제 안에서 유지한다. 제출 형식 안내를 매 시도 반복하지 않는다. 지시문이나 메시지 구성이 바뀐 실험은 새 실행 폴더에서 시작한다.

지시문에는 삭제 조작과 JSON 형식을 보여주는 영문 예시 세 개를 포함한다. `ABBBA`는 묶음 전체 삭제와 새로 합쳐진 묶음의 별도 삭제, `ACAADAAEAAB`는 단일 글자를 제외한 묶음 번호와 삭제 후 재번호 부여, `ABB ABB`는 공백을 가로질러 세는 묶음 번호와 공백으로 막힌 결합을 보여준다. 각 예시에는 시작 문자열, 동작별 상태, 제출 JSON만 제시하며 목표·금지쌍·정답 판정은 넣지 않는다. 예시는 문제 데이터와 독립적으로 고정하며, 모델과 사람 평가에 같은 지시문을 사용한다.

한 응답에 삭제 수순 `moves`와 그 순서로 남길 최종 문자열 `answer`를 함께 적는다. 수순은 `A2 B1 A1`처럼 글자와 번호를 적고 행동 사이를 공백 한 칸으로 구분한다. 예를 들어 입력 `ABB A`에서 B를 지워 A 두 개를 나눠 남기는 제출은 `{"moves":"B1","answer":"A A"}`다. 모두 지우는 계획은 `answer`에 빈 문자열을 넣는다. 기존 응답 `ABC`도 읽을 수 있으며 `A1 B1 C1`과 같다. 해당 번호의 묶음이 없으면 그 행동에서 재생을 중단한다.

| 참가자가 받는 피드백 | 판정 |
|---|---|
| `Correct` | 기본 삭제가 모두 가능하고 신고한 최종 답과 목표가 맞으며 금지쌍을 지켰다. |
| `Incorrect, but no rule violation` | 성공 조건을 충족하지 못했고 식별된 금지쌍 위반도 없다. |
| `Incorrect, also rule violation` | 금지쌍을 위반했고 성공적인 목표 도달을 확인하지 못했다. |
| `Correct, but rule violation` | 기본 삭제로 신고한 최종 답과 목표에 도달했으나 금지쌍을 위반했다. |

규칙 위반이 있으면 해당 제출에서 **최초로 위반한 삭제 동작의 위치 하나만** 영문으로 덧붙인다. 예를 들어 3·6·8번째 동작에서 위반했다면 `Correct, but rule violation. Rule violation: move 3.`처럼 전달하며, 최초 위반이라는 표현은 쓰지 않는다. 번호는 제출한 `moves`의 첫 동작을 1로 센 값이며, 금지된 연속 삭제쌍 중 두 번째 동작을 가리킨다. 문자열의 글자 위치나 `A2`의 묶음 번호가 아니다. 규칙 위반이 없으면 기존 문구만 전달한다. 모델의 다음 요청과 사람 평가 화면의 피드백·이전 기록에 같은 문구를 사용한다.

피드백이 바뀌기 전 실행은 현재 코드로 이어서 진행할 수 없다. 새 실행 폴더 또는 새 참가자 세션으로 시작한다.

매 제출은 그 라운드의 동일한 시작 문자열에서 진행한다. 라운드당 시도 한도(T)는 실행 설정을 따르며, 연속 정답 기준(k)은 기본 2회다. 오답을 받으면 연속 정답 수가 0으로 돌아가고, 기회를 소진하면 해당 문제의 남은 라운드를 건너뛴다.

같은 문제 안에서 이전 제출과 실제 삭제 수순이 일치했는지 따로 기록한다. 2라운드부터는 동일한 입력·목표·응답에 직전 금지쌍을 대입해 비교한다. 현재 규칙에서만 성공(`current_only`), 직전 규칙에서만 성공(`previous_only`), 양쪽 성공(`both`), 양쪽 실패(`neither`)로 구분한다.

## 인간 평가 화면

[human.html](web/human.html)은 참가자용 영문 화면이다. [human_server.py](human_server.py)를 실행하고 터미널에 표시된 주소로 접속한다. 지울 묶음을 직접 선택해 더 지울 묶음이 없는 상태까지 진행한 뒤 제출한다. 매 제출의 삭제 순서, 최종 문자열, 네 종류의 피드백이 현재 입력의 이전 기록에 추가된다. 빈 문자열은 `∅`로 표시한다.

이전 기록을 펼치면 시작 문자열과 각 삭제 후 문자열이 위에서 아래로 표시된다. 다음 시도를 푸는 중에도 이전 기록을 비교할 수 있다. 묶음 번호는 각 행동 시점의 문자열을 기준으로 해석한다. 피드백을 읽고 Continue를 누르면 다음 시도를 시작한다.

세션 식별자와 진행 중인 삭제는 같은 브라우저에 저장되며, 채점된 제출과 전체 평가 결과는 서버에 저장된다. 새로고침하거나 같은 제출을 재전송해도 이미 접수된 시도는 한 번만 집계한다. 완료된 세션의 기록도 다시 볼 수 있다.

서버는 참가자가 본 입력·제출·피드백만 브라우저에 전달한다. 문제 원본, 정답 파일, 검토 화면, 평가자용 보고서는 서버의 공개 경로에 포함하지 않는다. `review.html`은 평가자가 문제를 검토하는 별도 파일이다.

## 지속 오류 채점

R2~R5에서 현재 금지쌍을 한 번 이상 위반한 **제출 한 건**을 지속 오류 한 건으로 센다. 한 응답에서 같은 위반이 세 번 발생해도 분자는 1이다. 라운드 PER은 지속 오류 제출 수를 그 라운드에서 실제 채점한 제출 수로 나눈 값이다. 문제 MPE는 진행한 R2~R5의 PER 평균, 전체 MPE는 계산 가능한 문제들의 MPE 평균이다. R1은 일반 오답률에만 포함한다.

금지쌍을 위반해도 물리적으로 가능한 삭제는 계속 재생한다. 참가자가 제출한 삭제 순서 전체를 보고, 첫 물리적 오류가 나오면 그 위치까지 식별 가능한 위반을 센다. 참가자에게는 표의 피드백과 최초 규칙 위반 위치만 준다. 규칙 위반이 없는 물리적 오류에는 위치 안내를 추가하지 않는다. 전체 위반 위치, 행동별 진단과 PER 집계는 평가자용으로 유지한다. 최초 위치만 알려주어도 PER/MPE 집계 방식은 바뀌지 않는다.

## 문항 검증

검토 화면의 **도달 가능한 최종 조합 수**는 한 라운드에서 더 지울 수 없을 때까지 진행하는 방법을 센다. 처음 문자열에서 어느 위치의 글자들을 한 행동으로 함께 지웠는지 기록하고, 그 묶음들이 같으면 행동 순서가 달라도 한 번만 센다. 예를 들어 `AABB`는 `AA`와 `BB` 중 어느 쪽부터 지워도 빈 문자열로 끝나는 한 조합이다. 금지쌍 위반과 목표 길이를 벗어난 결말도 포함한다. **목표 글자 수에 맞는 조합**은 그중 마지막에 남은 글자 수가 목표와 같은 경우다. 최종 문자열별로 묶음 조합 수와 완주 예시를 볼 수 있다.

예를 들어 SG-001 1라운드의 전체 조합은 46가지이며, 최종 문자열은 10종이다. 그중 한 글자를 남기는 12가지 조합은 `B` 10가지, `C` 1가지, `E` 1가지다.

- 각 문자열에서 적어도 3개의 서로 다른 정답 삭제 순서가 있어야 한다.
- 모든 라운드에서 현재 금지쌍을 지키면서 목표에 성공하는 수순이 있고, 금지쌍을 지키고 물리적으로 끝까지 진행해도 다른 길이가 남아 실패하는 수순이 있다.
- 목표 1·2·3에서는 같은 목표 길이에서 남길 수 있는 글자 구성이 적어도 두 종류다. 예를 들어 `AB`와 `AC`는 두 종류로 세고, `AB`, `BA`, `A B`는 한 종류로 센다. 양수 목표별 라운드의 4분의 1 이상은 세 가지 이상의 서로 다른 글자 구성을 남길 수 있다.
- 목표 0에서는 정답이 빈 문자열 하나다. 같은 입력과 금지쌍으로 1~3글자를 남겨 끝나는 합법 수순도 있어야 한다. 목표 1·2·3에서도 지정 목표와 다른 0~3글자 길이로 끝나는 합법 수순을 확인한다. 여기서 끝난 상태는 같은 구간에 지울 묶음이 하나도 없는 상태다.
- 한 결말만 압도적으로 자주 나오는 판도 걸러낸다. 각 상태에서 현재 규칙상 선택할 수 있는 글자 중 하나를 같은 확률로 고르고, 그 글자의 지울 수 있는 묶음 중 하나를 다시 같은 확률로 고른다고 가정한다. 목표 1~3에서는 성공한 경우에 한 글자 구성이 차지하는 비율이 최대 95%여야 한다. 목표 0에서는 무작위로 골라 전부 지우는 확률이 최대 95%여야 한다. 이 기준은 참가자의 실제 응답 확률과 별도로 계산한다.
- 입력 길이만 보고 목표를 구별하기 어렵게 유형·라운드·목표별로 길이를 배분한다. 서로 다른 글자형의 R2~R5에서는 각 목표에 31글자와 32글자를 한 개 이내 차이로 배정한다. 나머지 유형·라운드·목표 조합에는 각각 28~32글자 길이를 모두 사용한다.
- 원래 분리된 묶음이 합쳐진 뒤 삭제되는 행동을 모든 성공 수순에서 최소 4회 요구한다. 그중 원래 한 글자였던 묶음끼리 합쳐져 삭제되는 행동이 최소 2회 필요하다. 공백 라운드에서는 경계를 없애면 실패하는 수순으로 대표 정답에 도달할 수 있어야 한다.
- R2~R5 전환 200개 각각에서, 현재 입력과 목표에 직전 금지쌍을 적용해 완주하는 수순을 탐색한다. 그 수순에서 다른 합법 행동으로 회복할 수 있었던 현재 규칙 위반이 최소 3회이고, 전체 행동의 40% 이상이어야 한다. 이 비율은 문항을 고르는 조건이다. 참가자의 PER은 제출 단위로 별도로 계산한다.

[generate.mjs](scripts/generate.mjs)가 고정 시드로 문제와 정답을 만들고, [grade.py](src/grade.py)가 독립적으로 검사한다.

## 실행

아래 명령은 `SameGame/` 폴더에서 Python 3.11 이상으로 실행한다. 기본 채점기와 사람 평가 서버는 Python 표준 라이브러리를 사용한다.

```sh
python3 -m src.grade --validate
python3 -m src.grade SG-001 1 --group-counts
```

두 번째 명령은 지정한 라운드의 도달 가능한 최종 조합 수, 목표 글자 수에 맞는 조합 수, 최종 답안별 조합 수를 출력한다.

```sh
python3 -m src.evaluate --item SG-001 --report results.json
```

이 명령은 참가자에게 보낼 영어 요청을 표준 출력에 JSON 한 줄로 쓰고, 표준 입력에서 한 줄에 한 응답을 받는다. 다른 프로그램에서 응답을 받아 연결하거나 직접 입력할 수 있다. 참가자에게는 요청과 피드백을 전달한다. 비공개 제출 기록과 PER/MPE는 `--report`에 지정한 파일에 기록한다. 모델이나 사람의 응답을 이미 수집했다면 한 줄에 한 응답을 쓴 파일로 순서대로 재생할 수 있다.

```sh
python3 -m src.evaluate --item SG-001 --responses submissions.jsonl --report results.json
```

`--item`을 생략하면 50문제를 순서대로 진행한다. 최종 문자열 하나의 도달 가능성만 검사하려면 `python3 -m src.grade SG-008 1 --answer 'A A'`를 사용한다. `node scripts/generate.mjs`는 문제와 정답을 재생성한다.

### 모델 평가

`tower-of-hanoi` 브랜치의 모델 ID와 추론 설정을 사용한다. 제공자별 설정 파일에서 모델을 선택한다.

| 설정 파일 | 프로필 | 모델 | 추론 강도 | 라운드당 최대 시도(T) |
|---|---|---|---|---|
| [configs/openai.toml](configs/openai.toml) | `sol` | `gpt-6.1-sol` | `medium` | 20 |
| [configs/anthropic.toml](configs/anthropic.toml) | `opus` | `claude-opus-5-5` | `medium` | 10 |
| [configs/anthropic.toml](configs/anthropic.toml) | `sonnet` | `claude-sonnet-5-5` | `medium` | 10 |

Sol 재실험은 T=20으로 설정한다. 모든 모델의 연속 정답 기준은 2회, 응답당 최대 25,000토큰, API 제한 시간 180초다. 첫 라운드에도 동일한 시도 한도와 연속 정답 조건을 적용한다. API 키는 실행 터미널의 `OPENAI_API_KEY` 또는 `ANTHROPIC_API_KEY` 환경 변수에서 읽는다.

```sh
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt

python run.py --config configs/openai.toml --profile sol --output runs/sol
python run.py --config configs/anthropic.toml --profile opus --output runs/opus
python run.py --config configs/anthropic.toml --profile sonnet --output runs/sonnet
```

설정을 먼저 확인하려면 다음 명령으로 첫 요청을 출력한다. `--dry-run`은 API 호출과 결과 파일 생성을 수행하지 않는다. `--item SG-001`로 특정 문제를, `--limit 1`로 앞의 한 문제를 선택할 수 있다.

```sh
python run.py --profile sol --limit 1 --dry-run
python run.py --resume runs/sol
```

`--resume`은 해당 실행 폴더에 저장된 T·k를 그대로 사용한다. 변경한 T=10을 적용하려면 새 실행 폴더로 시작한다. `python run.py --profile sol`처럼 `--output`을 생략하면 날짜·시간을 붙인 새 실행 폴더를 자동으로 만든다.

#### 추론 요약을 남기는 진단 실행

OpenAI 실행에서 `--reasoning-summary`를 지정하면 API가 제공하는 사람이 읽을 수 있는 추론 요약을 저장한다. 값을 생략하면 `auto`이며, `off`, `auto`, `concise`, `detailed` 중 선택할 수 있다. 기본값은 `off`다. 모델과 API가 지원하는 요약 수준을 사용하며, 암호화된 추론 원문을 복호화하는 옵션은 아니다. [OpenAI 추론 요약 문서](https://developers.openai.com/api/docs/guides/reasoning#reasoning-summaries)

```sh
python run.py --profile sol --reasoning-summary auto --output runs/sol_T20_summary
```

이 명령은 현재 Sol 설정(T=20, k=2)으로 50문제를 처음부터 실행한다. 앞의 두 문제만 진단하려면 `--limit 2`를 붙인다. 모델 프로필의 TOML 설정에 `reasoning_summary = "auto"`를 추가해 기본값으로 둘 수도 있으며, 명령행 옵션을 우선한다. Anthropic 실행에서는 이 옵션을 `off`로 둔다.

- `reasoning_log.txt`: 시도 순서대로 입력, 목표·규칙, API 추론 요약, 제출 원문, 피드백, 위반 위치를 모은 평가자용 기록.
- `submissions/00001_reasoning_summary.json`: 각 응답의 요약과 상태(`available` 또는 `empty`), 문제·라운드·시도 정보를 담은 구조화 기록.
- 기존 응답·스트림 파일에도 API가 반환한 원본 요약과 암호화된 추론 상태가 함께 보존된다.

요약 텍스트가 없으면 그 사실을 기록하고 원래 응답을 그대로 채점한다. 추가 호출이나 요약 생성으로 빈 내용을 채우지 않는다. 과제 지시문·제출 형식·네 가지 피드백은 그대로 사용하며, 평가자용 진단 정보는 모델에게 전달하지 않는다. 같은 문제 안에서는 요약을 포함한 제공자의 원본 응답 항목과 암호화된 추론 상태를 보존하고, 다음 문제에서 초기화한다.

진단 옵션은 새 실행의 `protocol.json`에 고정된다. 재개할 때는 `python run.py --resume runs/sol_T20_summary`만 사용한다. 기존 실행에 요약 옵션을 중간에 켜려면 새 실행 폴더가 필요하다. 이미 저장된 응답을 재사용하면 요약 기록도 중복 없이 복구된다. 요약은 모델 내부 과정을 모두 보여주는 기록은 아니므로 실제 제출·피드백과 함께 분석한다.

터미널에는 문제·라운드·시도 진행, 이전·현재 규칙, 응답 대기 시간, 피드백, 삭제 순서, 남은 문자열, 토큰 사용량과 MPE가 표시된다. 규칙은 `A → C 연속 삭제 금지`처럼 표시하고, 각 문제의 첫 라운드는 이전 규칙을 `없음 (첫 라운드)`으로 표시한다. 이전 규칙은 같은 문제의 직전 라운드를 기준으로 하며, 이 정보는 평가자용 터미널에만 표시한다. 파이프로 로그를 저장할 때는 고정된 줄로 출력하며 `NO_COLOR=1`로 색상을 끌 수 있다.

`현재 가능 정답`은 현재 입력에서 현재 규칙을 지키면서 목표에 도달할 수 있는 최종 문자열을 모두 표시한다. 같은 최종 문자열로 끝나는 여러 삭제 순서는 한 번만 표시하며, `"A A"`처럼 내부 공백을 보존하고 빈 문자열은 `∅ (빈 문자열)`로 표시한다. 응답을 받으면 `제출한 삭제`와 `제출한 답안`을 별도로 표시한다. 목록에 있는 문자열을 제출해도 실제 삭제 순서가 규칙을 위반하거나 그 문자열로 끝나지 않으면 정답으로 인정하지 않는다. 이 목록은 평가자용 터미널에만 표시되며, 모델 요청과 참가자 화면에는 전달하지 않는다.

각 실행 폴더에는 고정한 문제·설정을 담은 `protocol.json`, 재개 상태인 `checkpoint.json`, 평가 결과인 `report.json`, 제출별 요청·응답·스트림·채점 기록이 저장된다. 보고서는 기존 PER/MPE와 복사 응답 진단을 포함한다. 통신 실패는 시도를 소비하지 않으며, `--resume`은 저장된 완료 응답을 먼저 사용한다. 같은 실행 폴더에 대한 동시 실행은 차단한다.

같은 문제의 라운드 사이에는 제공자 고유의 추론 상태와 제출·피드백을 이어 보내고, 다음 문제에서 새 대화를 시작한다. OpenAI는 Responses API의 암호화된 reasoning 항목을, Anthropic은 Messages API의 원래 thinking 블록을 보존한다. [OpenAI 문서](https://developers.openai.com/api/docs/guides/reasoning), [Anthropic 문서](https://platform.claude.com/docs/en/build-with-claude/thinking)

### 사람 평가

```sh
python human_server.py --output runs/human
```

브라우저에서 `http://127.0.0.1:8765`에 접속한다. 참가자 ID는 선택 사항이다. `--item SG-001`, `--limit 1`, `--port 8766`도 사용할 수 있다. 다른 기기에서 접속하려면 평가자가 `--host`와 접근 가능한 네트워크 주소를 지정한다.

참가자별 서버 저장 파일은 `runs/human/sessions/<세션 식별자>.json`이다. 선택한 문제와 진행 설정, 제출 기록, `report` 안의 PER/MPE가 함께 저장된다. 같은 출력 폴더로 서버를 다시 실행하면 기존 참가자가 이어서 진행할 수 있다. 재개할 때는 저장 당시의 지시문과 채점 코드를 사용한다.

### 파일 구성

루트에는 실행 진입점과 설치·사용 안내를 두고, 데이터·평가 코드·화면·문제 생성·테스트를 역할별로 구분한다.

```text
SameGame/
├── README.md
├── requirements.txt
├── run.py                 # 모델 평가 실행
├── human_server.py        # 사람 평가 서버 실행
├── configs/               # OpenAI·Anthropic 설정
├── data/
│   ├── problems.json      # 평가자용 문제 원본
│   └── answer_key.json    # 대표 정답
├── src/
│   ├── _paths.py          # 공통 파일 경로
│   ├── evaluate.py        # 지시문·피드백·라운드 진행·PER/MPE
│   ├── grade.py           # 삭제 처리·채점·문항 검증
│   ├── model_runner.py    # 모델 실행·저장·재개
│   ├── providers.py       # OpenAI·Anthropic API 연결
│   ├── diagnostics.py     # 선택적 추론 요약·진단 기록
│   └── human_server.py    # 참가자 세션·HTTP 처리
├── web/
│   ├── human.html         # 참가자용 화면
│   └── review.html        # 평가자용 문제 검토
├── scripts/
│   ├── generate.mjs       # 문제·정답 생성
│   └── solve.mjs          # 풀이 탐색
├── tests/                 # 채점·세션·모델 실행 테스트
└── runs/                  # 실행 시 생성되는 결과·참가자 기록
```

`run.py`와 `human_server.py`는 `src/`의 구현을 호출한다. 생성기는 결과를 `data/`에 저장한다. 실행 결과와 가상 환경은 `.gitignore`로 제외한다.

공통 채점과 서버·모델 실행 검사는 다음 명령으로 실행한다.

```sh
python -m unittest discover -s tests -q
```

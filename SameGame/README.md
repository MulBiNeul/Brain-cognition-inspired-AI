# SameGame · 연속 삭제 금지

영문 문자열을 쓰는 50문제 파일럿이다. 한 문제는 5라운드이며 각 라운드에 입력 문자열 하나가 있다. 다음 라운드로 바뀌면 입력, 목표 글자 수, 금지하는 연속 행동쌍이 모두 달라진다. [review.html](web/review.html)을 브라우저에서 열면 250개 라운드를 오프라인으로 직접 검토할 수 있다.

2026-11-12 확인한 지속 오류 기준은 **이전 규칙을 지키면서 현재 문제에서는 오답인 제출**이다. 현재 문자열에서 기본 삭제를 끝까지 수행하고 최종 문자열을 정확히 제출한 경우에 한해 판정한다. 정답은 지속 오류가 아니며, 직전 금지쌍 위반 자체를 세지도 않는다. 라운드 PER의 분모는 최대 시도 수 T로 고정한다. 기존 실행 결과는 보존하며, 자세한 운용 정의와 과거 지표와의 차이는 [지속 오류 채점](#지속-오류-채점)을 따른다.

| 문제 | 유형 | 금지쌍의 의미 |
|---|---|---|
| SG-001~SG-025 | 서로 다른 글자 | `AC`이면 A를 지운 바로 다음 행동으로 C를 지울 수 없다. `CA`와 `ABC`는 허용된다. 다음 라운드에는 쌍의 한쪽 글자가 바뀐다. |
| SG-026~SG-050 | 같은 글자 | `BB`이면 B를 두 행동 연속으로 선택할 수 없다. `BBB` 묶음 한 번을 지우는 것은 한 행동이다. 다섯 라운드에서 `AA`~`EE`가 한 번씩 나온다. |

## 삭제와 최종 목표

입력은 A–E를 모두 포함하는 28~32글자 문자열이다. 같은 글자가 두 개 이상 붙어 있는 묶음 중 원하는 하나를 골라 전부 지운다. 검토 화면에서는 문자열 위의 묶음을 직접 누른다. 사이가 비면 같은 구간의 양옆 글자가 붙는다. 새로 붙은 묶음도 다시 선택해야 지워진다. 매 제출은 해당 라운드의 입력에서 다시 시작하며 직전 행동도 초기화한다.

수순의 `A2`는 현재 지울 수 있는 A 묶음 중 왼쪽에서 두 번째를 뜻한다. 한 글자짜리 A는 번호에서 제외하고, 공백 양쪽에 A 묶음이 있으면 왼쪽부터 이어서 번호를 붙인다. 한 수를 둘 때마다 현재 문자열에서 다시 센다. 금지쌍은 선택한 글자만 본다. 예를 들어 `B2 B1`도 `BB` 위반이다.

30문제에는 공백이 없고, 20문제에는 라운드마다 영구 경계인 공백 한 칸이 있다. 예를 들어 `ABBA`에서 B를 지우면 `AA`가 되어 다음에 A를 지울 수 있다. `ABB A`에서 B를 지우면 `A A`가 되고, 두 A는 계속 분리된다.

**종료 조건은 지울 수 있는 묶음이 하나도 없는 상태**다. 묶음이 있으면 목표 길이에 도달했거나 남은 선택이 금지쌍을 위반해도 계속 지운다. 위반 위치는 기록하고, 정오와 피드백은 제출한 수순을 재생해 판정한다. 묶음이 남아 있는데 제출 수순이 끝나면 미완료다.

예를 들어 `ABBAC`에서 B를 지우면 `AAC`다. 3글자가 남았어도 `AA`를 더 지워야 한다. 금지쌍이 `BA`여도 A 삭제는 실행되고, 최종 문자열은 `C`, 위반 위치는 2번째 행동이다.

예를 들어 목표가 모두 삭제이고 금지쌍이 `EE`일 때, `AABAABA`에서 왼쪽 `AA`를 먼저 고르면 `BAABA → BBA → A`로 끝난다. 오른쪽 `AA`를 먼저 고르는 수순 `A2 B1 A1`은 `AABBA → AAA → 빈 문자열`로 끝난다.

목표는 0·1·2·3글자 남기기 중 하나다. 한 문제에서 네 목표를 모두 사용하고 연속한 두 라운드의 목표는 다르다. 남기는 알파벳은 자유이며, 최종 문자열에는 같은 구간 안에 연속된 동일 글자가 없어야 한다. 아래 예시가 정답이 되려면 해당 입력에서 실제로 도달할 수 있어야 한다.

| 목표 | 허용되는 최종 형태의 예 | 실패하는 최종 형태의 예 |
|---|---|---|
| 0 | `""` (빈 문자열) | `A` |
| 1 | `A`, `E` | `AB` |
| 2 | `AB`, `A B`, `A A` | `AA`, `BB` |
| 3 | `ABA`, `AB A`, `A AB` | `AAB`, `ABB`, `AA B`, `A AA` |

공백은 글자 수에서 제외하고, 살아남은 글자 사이에 있으면 최종 답에 그대로 쓴다. 맨 앞이나 끝의 공백은 생략한다. [answer_key.json](data/answer_key.json)에는 각 라운드의 대표 최종 문자열을 `answer`에 담는다. 참가자의 다른 도달 가능한 답도 인정한다.

## R1 난이도 완화 버전

[data/easy_r1/problems.json](data/easy_r1/problems.json)은 기존 50문제의 첫 라운드를 쉽게 만든 별도 비교용 데이터다. 기본 문제·정답 파일과 기존 실행 기록은 유지한다. 문제 ID, 유형, 목표·규칙 순서, R1의 글자 수와 공백 유무를 원본과 맞추고, R2~R5의 입력과 정답은 그대로 복사한다.

R1은 큰 묶음을 늘려 더 짧은 삭제 수순으로 풀 수 있도록 구성한다. 필수 합쳐진 묶음 삭제는 최소 4회에서 2회, 필수 단일 글자끼리 합치기는 최소 2회에서 1회로 완화하고, R1에만 있던 가상의 이전 규칙 비교 조건은 적용하지 않는다. 중간을 지워 묶음을 합치는 조작, 여러 정답 수순, 서로 다른 최종 글자 구성, 규칙을 지켜도 목표를 놓칠 수 있는 경로는 유지한다. 실제 수순 길이와 검증 결과는 [design_report.json](data/easy_r1/design_report.json)에 기록한다.

현재 규칙이 의미 없는 문항은 제외한다. 모든 R1에는 규칙을 지켜 목표에 도달하는 경로와, 목표 글자 수는 맞추지만 현재 규칙을 위반하는 경로가 모두 있다. 두 경로와 규칙을 지키며 다른 목표 글자 수로 끝나는 경로를 설계 보고서에 남긴다.

생성된 50개 R1의 측정값은 다음과 같다. 모든 새 R1에서 가장 긴 정답 수순도 대응하는 원본 R1의 가장 짧은 정답 수순보다 짧다. 실제 모델의 성공률 개선은 새 실행으로 확인해야 한다.

| R1 지표 | 원본 | 완화 버전 |
|---|---|---|
| 최단 정답 수순 | 10~15회, 중앙값 12회 | 8~9회, 중앙값 8회 |
| 최장 정답 수순 | 12~16회, 중앙값 13회 | 9~10회, 중앙값 9회 |
| 모든 성공 경로에서 필요한 합쳐진 묶음 삭제의 최소 횟수 | 4~9회 | 2~3회 |
| 위 합치기 중 단일 글자끼리 합치는 삭제의 최소 횟수 | 2~9회 | 1~2회 |

쉬운 버전 생성·검증과 검토 화면 생성:

```sh
python scripts/generate_easy.py
python scripts/generate_easy.py --validate-only
python scripts/build_review.py --data-dir data/easy_r1 --output web/review_easy_r1.html
```

[review_easy_r1.html](web/review_easy_r1.html)을 열어 직접 풀어볼 수 있다. 기본 문제는 기존 [review.html](web/review.html)에서 검토한다. 완화 버전은 전용 `--validate-only`로 검증하며, 기본 문제의 강한 합치기 조건을 검사하는 `python -m src.grade --validate`는 기본 데이터 검증에 사용한다.

새 실행 폴더로 비교 실험을 시작한다. 모든 프로필은 T=10, k=2이며, 지시문·전체 위반 위치 피드백은 기본 버전과 같다. 데이터 버전과 별개로 새 실행은 아래의 ‘이전 규칙 준수·현재 오답’ 기준과 고정 T 분모로 PER/MPE를 계산한다.

```sh
python run.py --config configs/openai_easy_r1.toml --profile sol --reasoning-summary auto --output runs/sol_easy_r1
python run.py --config configs/anthropic_easy_r1.toml --profile opus --output runs/opus_easy_r1
python run.py --config configs/anthropic_easy_r1.toml --profile sonnet --output runs/sonnet_easy_r1
python human_server.py --data-dir data/easy_r1 --output runs/human_easy_r1
```

기본 `--profile sol` 명령과 원래 설정 파일은 기존 문제를 계속 사용한다. 결과 비교에서는 초기 R1 통과율과 R2 진입 수를 함께 보고, 데이터가 다른 실행의 MPE를 하나로 합산하지 않는다.

## 전체 라운드 난이도 완화 버전

[data/easy_all/problems.json](data/easy_all/problems.json)은 50문제의 5개 라운드 모두를 완화한 별도 데이터다. R1은 `easy_r1`의 50개 라운드를 그대로 사용하고, R2~R5 200개를 다시 생성한다. 기본 데이터와 R1 전용 완화 데이터는 보존한다. 문제별 유형, 규칙·목표 순서, 각 입력의 글자 수와 공백 유무는 기본 데이터와 같다.

새 라운드에는 원본보다 짧은 정답 수순이 존재하도록 하고, 최단 정답 수순을 8~12회로 제한한다. 모든 성공 경로에서 합쳐진 묶음 삭제 최소 2회와 단일 글자끼리 합친 삭제 최소 1회를 요구한다. 여러 정답 수순·최종 글자 구성, 규칙을 지키면서 다른 0~3글자로 끝나는 경로, 공백으로 인한 결합 차이는 유지한다. 최단 수순 기준이므로 모든 정답 수순이 12회 이하인 것은 아니다.

생성된 R2~R5 200개의 측정값은 다음과 같다. 실제로 200개 모두 최단·최장 정답 수순이 원본보다 짧다. 모델의 성공률 개선은 별도 실행으로 확인해야 한다.

| R2~R5 지표 | 원본 중앙값 | 전체 완화 중앙값 |
|---|---:|---:|
| 최단 정답 수순 | 12회 | 10회 |
| 최장 정답 수순 | 14회 | 11회 |
| 필수 합쳐진 묶음 삭제의 최소 횟수 | 5회 | 4회 |
| 필수 단일 글자끼리 합치는 삭제의 최소 횟수 | 5회 | 3회 |
| 시작 상태의 삭제 선택지 | 8개 | 7개 |

R2~R5에는 **이전 규칙으로 목표에 도달하지만 현재 규칙을 회복 가능한 지점에서 최소 3회 위반하는 수순**이 있다. 반대로 현재 규칙의 대표 정답은 이전 규칙을 위반하도록 하여 두 규칙을 구분한다. 생성 시 사용하던 ‘해당 수순 행동의 40% 이상 위반’ 조건은 이 버전에서 제거하고 실제 비율을 보고서에 남긴다. 서로 다른 글자 금지쌍과 목표 0에서 이 조건을 유지하면 최소 15행동이 필요해 전체 완화를 제한하기 때문이다. 이 생성 선별 비율은 제출 단위 PER/MPE와 별개다. 데이터 생성 당시에는 평가 수식과 피드백을 변경하지 않았으나, 현재 실행의 지속 오류는 아래에서 정의한 ‘이전 규칙 준수·현재 오답’ 기준으로 계산한다.

새 전환 수순의 회복 가능한 위반 행동 비율은 27.27~45.45%이며 중앙값은 33.33%다. 200개 중 163개는 예전 40% 선별 조건을 만족하지 않는다. 이 수치는 생성된 예시 수순의 특성이고 모델의 MPE 측정값은 아니다.

[review_easy_all.html](web/review_easy_all.html)에서 전체 완화 문제를 검토하고, [design_report.json](data/easy_all/design_report.json)에서 원본 대비 수순 길이와 전환별 위반 경로를 확인한다.

```sh
python scripts/generate_easy_all.py --validate-only
python scripts/build_review.py --data-dir data/easy_all --output web/review_easy_all.html --variant easy_all
python run.py --config configs/openai_easy_all.toml --profile sol --reasoning-summary auto --output runs/sol_easy_all
python run.py --config configs/anthropic_easy_all.toml --profile opus --output runs/opus_easy_all
python run.py --config configs/anthropic_easy_all.toml --profile sonnet --output runs/sonnet_easy_all
python human_server.py --data-dir data/easy_all --output runs/human_easy_all
```

고정 시드로 다시 생성하려면 `python scripts/generate_easy_all.py`를 사용한다. 기존 실행을 이 데이터로 바꿔 재개하지 않고 새 실행 폴더에서 시작한다. 모델 성능 비교에서는 라운드별 통과율과 도달한 라운드 수, MPE를 함께 본다.

## 같은 문자형 공통 회피 전략 수정 버전

`easy_all`의 같은 문자형에는 어떤 글자도 두 행동 연속으로 삭제하지 않고 목표에 도달하는 수순이 있었다. 그런 수순은 `AA`~`EE` 금지를 모두 만족하므로, 현재 금지 글자를 구분하지 않고도 규칙을 지킬 수 있다.

[data/easy_same_letter_v2/problems.json](data/easy_same_letter_v2/problems.json)은 이 경로를 제거한 별도 50문제 데이터다. 다른 문자형 SG-001~SG-025는 `easy_all`과 동일하고, 같은 문자형 SG-026~SG-050의 R1~R5 125개 입력을 새로 생성한다. 문제 ID, 유형, 라운드별 목표·금지쌍, 정확한 글자 수와 공백 유무를 유지한다. 기존 데이터와 `runs/sol_easy_all` 결과는 보존한다.

새 조건은 대표 정답 하나에만 적용하지 않는다. 가능한 삭제 상태와 직전 삭제 글자를 함께 탐색해 **모든 규칙 준수 정답에 동일 글자 연속 삭제가 최소 한 번 필요함**을 확인한다. 반복하는 글자는 현재 금지 글자일 수 없다. 이전·현재 두 규칙을 모두 지키는 정답은 여전히 허용한다. 지시문·피드백·채점 수식에 이 생성 조건을 추가하지 않는다.

이 버전은 우회 수순 제거를 우선하여 생성 선별 조건도 조정한다. R1의 묶음 합치기 횟수 상한을 제거하되 합치기 최소 2회·단일 글자 합치기 최소 1회는 유지한다. 전환 라운드에는 이전 규칙으로는 정답이지만 현재 규칙을 회복 가능한 지점에서 최소 1회 위반하는 수순을 요구하고, 기존의 최소 3회 조건과 차이를 보고서에 기록한다. 현재 규칙의 정답이 반드시 이전 규칙을 위반할 필요는 없다. 현재 규칙으로만 성공하는 수순은 존재할 때 별도로 기록한다. 따라서 이전 실행과의 비교는 우회 수순 제거뿐 아니라 이 생성 조건 변경도 포함한 데이터 버전 비교다.

R1의 최단 정답 수순은 8~10회로 유지한다. 공백이 있고 목표가 1글자인 R1에 한해 최장 정답 수순을 11회까지 허용하고, 다른 R1은 최장 10회로 제한한다. R2~R5는 최단 8~12회, 최장 13회 이하다. 양수 목표에서 서로 다른 최종 글자 구성은 반드시 두 종류 이상이다. 이전의 ‘목표별 최소 25%에서 구성 세 종류 이상’ 선별 조건은 적용하지 않고, 실제 분포를 보고서에 기록한다.

```sh
python scripts/generate_same_letter.py --validate-only
python scripts/build_review.py --variant easy_same_letter_v2
```

[review_easy_same_letter_v2.html](web/review_easy_same_letter_v2.html)에서 전체 50문제를 검토할 수 있다. 검사 수치와 증거 수순은 [design_report.json](data/easy_same_letter_v2/design_report.json)에 기록한다.

수정한 125라운드의 독립 검증에서 공통 회피 수순은 0개였다. 정답에 필요한 동일 글자 연속 삭제의 최솟값은 114라운드에서 1회, 11라운드에서 2회다. R2~R5의 이전 규칙 수순에서 회복 가능한 현재 규칙 위반은 1회인 라운드 73개, 2회 25개, 3회 2개다. 100개 전환 라운드의 대표 정답은 이전·현재 규칙을 모두 지킨다. 같은 문자형에서 목표 1·2의 최종 글자 구성은 각각 모든 31라운드에서 두 종류이고, 목표 3은 31개 중 27라운드에서 세 종류 이상이다.

현재 정답은 이전 규칙 준수 여부와 관계없이 지속 오류 0건이다. v2의 같은 문자형 125라운드에는 모두 현재 정답이 존재하며, 100개 전환 라운드에는 **이전 규칙을 지키면서 현재 규칙을 위반해 오답이 되는 완결 수순**이 있다. 보고서의 `previous_rule_probe`가 이 경우를 보여 주므로, 확인된 새 기준에서 지속 오류가 발생할 수 있는 라운드는 100/100개다.

이전에 적었던 ‘직전 금지쌍을 위반할 수 없으므로 지속 오류를 측정할 수 없다’는 결론은 잘못 해석한 지표를 적용한 것이었다. 이전 금지쌍 위반이 불가능하다는 구조적 사실과 새 지속 오류의 발생 가능성은 다르다. 정답 수순에서 어떤 글자도 반복하지 않는 우회 경로를 차단한 검증 결과도 그대로 유효하다. 현재는 지표 정의 확인과 저장 응답 재채점을 먼저 진행하며, 이 오해를 이유로 문제를 대규모 재생성하지 않는다. 아래 명령은 데이터 선택과 실행 방식에 대한 안내이며, 이번 검토에서 새 API 실험을 시작하지 않았다.

재실행 전용 설정은 [same_letter/problems.json](data/easy_same_letter_v2/same_letter/problems.json)에 분리한 **같은 문자형 25문제만** 선택한다. Sol 설정은 이전 실험과 같은 medium, T=10, k=2, 최대 25,000토큰, timeout 600초, 추론 요약 auto다.

```sh
python run.py --config configs/openai_easy_same_letter_v2.toml --profile sol --dry-run
python run.py --config configs/openai_easy_same_letter_v2.toml --profile sol --output runs/sol_easy_same_letter_v2
python run.py --resume runs/sol_easy_same_letter_v2
```

새 데이터는 새 결과 폴더에서 시작한다. 이전 실행을 새 데이터로 바꿔 재개하지 않는다. 이전 같은 문자형 25문제와 새 25문제의 완주율·라운드 진입 수를 비교하고, MPE는 같은 지시변수와 분모로 재채점한 값끼리 비교한다. 기존 `runs/sol_easy_all`의 MPE는 현재 규칙 위반·실제 제출 수 분모 기준이므로 새 MPE와 직접 합산하지 않는다. 다른 문자형 결과를 재사용할 때도 실행 출처·데이터 버전·지속 오류 기준·분모를 함께 명시한다.

## 참가자에게 제시하는 것과 제출 방식

하노이탑 평가처럼 참가자는 기본 삭제 조작과 제출 형식, 현재 문자열을 받고 이전 제출과 피드백을 참고해 다음 계획을 제출한다. 목표의 종류·범위, 금지 규칙의 형태·내용, 라운드 번호와 전환 안내는 평가자만 본다. 예를 들어 목표가 남길 글자 수라는 점이나 규칙이 연속 삭제 금지쌍이라는 점도 평가자용 정보다. 모델에 전달되는 지시문은 [evaluate.py](src/evaluate.py)의 `INSTRUCTIONS`에 있으며, [problems.json](data/problems.json)은 목표와 금지쌍을 포함하는 평가자용 원본이다.

기본 조작, 피드백 활용, 제출 형식, 도구 사용 제한을 하나의 시스템 지시문으로 전달한다. OpenAI의 `instructions` 또는 Anthropic의 `system`에 같은 내용을 넣고, 사용자 메시지에 지시문을 다시 추가하지 않는다. 각 시도에는 `Initial string: "..."`만 새로 전달하며, 이전 응답·피드백·추론 상태는 같은 문제 안에서 유지한다. 제출 형식 안내를 매 시도 반복하지 않는다. 지시문이나 메시지 구성이 바뀐 실험은 새 실행 폴더에서 시작한다.

지시문에는 삭제 조작과 JSON 형식을 보여주는 영문 예시 세 개를 포함한다. `ABBBA`는 묶음 전체 삭제와 새로 합쳐진 묶음의 별도 삭제, `ACAADAAEAAB`는 단일 글자를 제외한 묶음 번호와 삭제 후 재번호 부여, `ABB ABB`는 공백을 가로질러 세는 묶음 번호와 공백으로 막힌 결합을 보여준다. 각 예시에는 시작 문자열, 동작별 상태, 제출 JSON만 제시하며 목표·금지쌍·정답 판정은 넣지 않는다. 예시는 문제 데이터와 독립적으로 고정하며, 모델과 사람 평가에 같은 지시문을 사용한다.

한 응답에 삭제 수순 `moves`와 그 순서로 남길 최종 문자열 `answer`를 함께 적는다. 수순은 `A2 B1 A1`처럼 글자와 번호를 적고 행동 사이를 공백 한 칸으로 구분한다. 예를 들어 입력 `ABB A`에서 B를 지워 A 두 개를 나눠 남기는 제출은 `{"moves":"B1","answer":"A A"}`다. 모두 지우는 계획은 `answer`에 빈 문자열을 넣는다. 기존 응답 `ABC`도 읽을 수 있으며 `A1 B1 C1`과 같다. 해당 번호의 묶음이 없으면 그 행동에서 재생을 중단한다.

| 참가자가 받는 피드백 | 판정 |
|---|---|
| `Correct` | 기본 삭제가 모두 가능하고 신고한 최종 답과 현재 목표가 맞으며 현재 금지쌍을 지켰다. |
| `Incorrect, but no rule violation` | 성공 조건을 충족하지 못했고 식별된 현재 금지쌍 위반도 없다. |
| `Incorrect, also rule violation` | 현재 금지쌍을 위반했고 성공적인 목표 도달을 확인하지 못했다. |
| `Correct, but rule violation` | 기본 삭제로 신고한 최종 답과 현재 목표에 도달했으나 현재 금지쌍을 위반했다. |

현재 규칙 위반이 있으면 해당 제출에서 **식별된 모든 현재 규칙 위반 동작의 위치**를 영문으로 덧붙인다. 예를 들어 3·6·8번째 동작에서 위반했다면 `Correct, but rule violation. Rule violation: moves 3, 6, 8.`처럼 전달한다. 한 번만 위반했다면 `Rule violation: move 3.`처럼 단수로 표시한다. 번호는 제출한 `moves`의 첫 동작을 1로 센 값이며, 금지된 연속 삭제쌍 중 두 번째 동작을 가리킨다. 문자열의 글자 위치나 `A2`의 묶음 번호가 아니다. 현재 규칙 위반이 없으면 기존 문구만 전달한다. 모델의 다음 요청과 사람 평가 화면의 피드백·이전 기록에 같은 문구를 사용하며, 이전 규칙 위반 위치나 지속 오류 여부는 참가자에게 추가로 전달하지 않는다.

피드백이나 채점 기준이 다른 실행은 현재 코드로 이어서 진행할 수 없다. 새 실행 폴더 또는 새 참가자 세션으로 시작한다.

매 제출은 그 라운드의 동일한 시작 문자열에서 진행한다. 라운드당 시도 한도(T)는 실행 설정을 따르며, 연속 정답 기준(k)은 기본 2회다. 현재 규칙과 목표에 따른 정답이면 이전 규칙 위반 여부와 무관하게 연속 정답 수가 증가한다. 오답을 받으면 연속 정답 수가 0으로 돌아가고, 기회를 소진하면 해당 문제의 남은 라운드를 건너뛴다.

같은 문제 안에서 이전 제출과 실제 삭제 수순이 일치했는지 따로 기록한다. 2라운드부터는 동일한 현재 입력·현재 목표·응답에 직전 금지쌍을 대입한 진단값도 남긴다. 현재 규칙에서만 성공(`current_only`), 직전 규칙에서만 성공(`previous_only`), 양쪽 성공(`both`), 양쪽 실패(`neither`)로 구분한다. 이 진단의 `previous_success`는 현재 목표 달성까지 요구하지만, 아래 지속 오류의 이전 규칙 준수 조건은 목표 달성을 요구하지 않는다. 따라서 이 진단값이나 이전 정답과의 단순 일치 여부만으로 PE를 계산하지 않는다.

## 인간 평가 화면

[human.html](web/human.html)은 참가자용 영문 화면이다. [human_server.py](human_server.py)를 실행하고 터미널에 표시된 주소로 접속한다. 지울 묶음을 직접 선택해 더 지울 묶음이 없는 상태까지 진행한 뒤 제출한다. 매 제출의 삭제 순서, 최종 문자열, 네 종류의 피드백이 현재 입력의 이전 기록에 추가된다. 빈 문자열은 `∅`로 표시한다.

이전 기록을 펼치면 시작 문자열과 각 삭제 후 문자열이 위에서 아래로 표시된다. 다음 시도를 푸는 중에도 이전 기록을 비교할 수 있다. 묶음 번호는 각 행동 시점의 문자열을 기준으로 해석한다. 피드백을 읽고 Continue를 누르면 다음 시도를 시작한다.

세션 식별자와 진행 중인 삭제는 같은 브라우저에 저장되며, 채점된 제출과 전체 평가 결과는 서버에 저장된다. 새로고침하거나 같은 제출을 재전송해도 이미 접수된 시도는 한 번만 집계한다. 완료된 세션의 기록도 다시 볼 수 있다.

서버는 참가자가 본 입력·제출·피드백만 브라우저에 전달한다. 문제 원본, 정답 파일, 검토 화면, 평가자용 보고서는 서버의 공개 경로에 포함하지 않는다. `review.html`은 평가자가 문제를 검토하는 별도 파일이다.

## 지속 오류 채점

사용자가 제시한 이미지에는 ‘이전 라운드에서는 정답이지만 현재 라운드에서는 실패한 응답’을 지시변수로 두고, 최대 반복 수 T로 나누는 수식이 있다. 이후 사용자가 **이전 규칙을 지키면서 현재 문제는 오답인 경우**라고 구체화한 내용을 SameGame에 다음과 같이 적용한다. 현재 문자열에서 제출을 재생하며, 이전 라운드의 입력이나 목표로 전체 문제를 다시 풀어 보지는 않는다. 현재 목표를 놓친 오답도 아래 조건을 만족하면 포함한다.

R2~R5에서 다음 조건을 모두 만족한 제출을 지속 오류 한 건으로 센다.

1. 제출 형식이 유효하다(`parse_valid`).
2. 제출한 삭제가 모두 물리적으로 가능하다(`base_valid`).
3. 더 지울 묶음이 없는 상태까지 진행했다(`board_exhausted`).
4. 제출한 최종 문자열이 실제 삭제 결과와 일치한다(`final_matches`).
5. 직전 라운드의 금지쌍을 위반하지 않았다.
6. 현재 규칙과 현재 목표 기준으로는 오답이다(`not correct`).

즉 `a = 완결된 유효 제출 ∧ 이전 규칙 준수 ∧ 현재 오답`이다. 현재 정답이면 이전 규칙 준수 여부와 관계없이 항상 PE=0이다. 직전 금지쌍을 위반했다면 현재 오답이어도 PE=0이다. 동일 제출에 현재 규칙 위반이 여러 번 있어도 분자는 최대 1이다. 형식 오류, 불가능한 삭제, 미완결 수순, 최종 문자열 불일치는 일반 오답으로 기록하되 PE로 세지 않는다.

| 완결된 유효 제출의 현재 결과 | 이전 규칙 | 지속 오류 | 연속 정답에 포함 |
|---|---|---|---|
| 정답 | 준수 또는 위반 | 0 | 예 |
| 현재 규칙 위반으로 오답 | 준수 | 1 | 아니요 |
| 현재 규칙은 지켰지만 목표가 달라 오답 | 준수 | 1 | 아니요 |
| 오답 | 위반 | 0 | 아니요 |

정답·참가자 피드백·연속 정답은 현재 규칙과 현재 목표로 판정한다. 금지쌍을 위반해도 물리적으로 가능한 삭제는 계속 재생하고, 첫 물리적 오류에서 멈춘다. 그 위치까지 식별 가능한 현재·이전 규칙 위반은 진단용으로 기록하지만, 기본 조작 오류가 있으면 위 PE 조건을 충족하지 못한다. 참가자에게는 현재 규칙 기준의 피드백과 위반 위치만 주며, 이전 규칙 위반 위치와 지속 오류 여부는 평가자용으로 유지한다.

지속 오류 제출 수를 E, 실제 채점한 제출 수를 n, 최대 시도 수를 T라고 할 때 지표는 다음과 같다. JSON은 0~1 비율로 저장하고 화면에서는 백분율로 표시한다.

- **라운드 PER = E/T.** k회 연속 정답으로 일찍 종료해도 분모 T를 유지한다. 남은 시도의 응답을 만들거나 오류를 추정하지 않고, 관측한 오류 횟수만 고정 예산으로 나눈다.
- **관측 제출 기준 `observed_per` = E/n.** 실제로 받은 응답 중 오류 비율을 보는 보조 지표이며, 기본 PER과 구분한다.
- **문제 MPE:** 실제 채점이 있는 R2~R5의 PER을 동일 가중치로 평균한다.
- **전체·유형별 MPE:** 해당 범위에서 계산 가능한 문제 MPE를 동일 가중치로 평균한다. `observed_mpe`는 같은 평균 순서로 관측 제출 기준 값을 모은 보조 지표다.

예를 들어 T=10에서 세 번 제출한 뒤 종료했고 PE가 한 건이면 PER은 10%, `observed_per`는 약 33.3%다. 직전 규칙이 없는 R1과 미진입·미채점 라운드는 `None`으로 두고 MPE 평균에서 제외한다. 미진입 라운드를 0으로 채우지 않는다. 이는 라운드 안에서 분모를 T로 고정하는 처리와 별개다. 도달한 전환 라운드 수와 예정 수, 실제 제출 수, MPE에 포함된 문제 수를 함께 보고하여 부분 진행 결과를 구분한다. 조기 종료한 문제와 앞 라운드에서 실패한 문제를 같은 관측 범위로 오해하지 않도록 한다.

새 실행의 `protocol.json`과 보고서에는 `persistent_error_basis: "previous_rule_compliant_current_incorrect"`를 기록한다. 요약과 유형별 요약의 `per_denominator`는 `"max_attempts"`, 라운드의 `per_denominator`는 해당 T이며 R1은 `None`이다. `previous_success`와 `previous_only`는 현재 목표까지 포함한 별도 진단이므로 PE를 대신하지 않는다.

기존 `runs/sol_easy_all` 등은 현재 규칙 위반을 실제 제출 수로 나눈 기준으로 계산된 결과다. 원본을 덮어쓰거나 새 기준으로 이어서 진행하지 않는다. 저장된 응답을 새 기준으로 별도 재채점하고, 지시변수와 분모가 같은 결과끼리 비교한다. 확인한 하노이탑 브랜치도 현재 규칙 위반·실제 제출 수 기준이므로 이번 운용 정의와 다르며, 이번 작업에서 하노이탑 코드는 변경하지 않았다. 데이터 설계 보고서의 `per_mpe_scoring_changed: false`는 해당 데이터 생성 당시의 변경 범위를 뜻하고, 현재 지표 기준은 실행 프로토콜을 따른다.

완료된 `sol_easy_all` 50문제를 2026-11-12에 새 기준으로 재집계했다. 저장된 935개 제출의 정답·피드백·라운드 진행은 모두 원본과 일치했고, 모델 호출은 0회였다. 결과는 [분석 비교표](runs/sol_easy_all/analysis_previous_rule_compliance_20261112/comparison.json)와 [재채점 보고서](runs/sol_easy_all/analysis_previous_rule_compliance_20261112/report.json)에 별도로 저장했다.

하노이탑의 `previous_success` 역시 현재 입력·현재 목표에 이전 규칙만 대입한 진단이며, 기존 PE 분자에는 사용하지 않는다. 따라서 단순히 ‘하노이탑과 같은 수식’이라고 표현하면 현재 두 구현의 차이를 놓친다. SameGame의 새 PE 정의·분모에 맞춰 비교하려면 하노이탑도 저장된 수순을 별도로 재채점해야 한다.

터미널의 토큰은 한 요청의 API 집계다. 입력은 지시문·문제·문제 내 이전 응답과 피드백 등을 포함하며, 출력은 답안과 추론 사용량을 포함할 수 있다. 누적 합계나 답안 문자열 길이가 아니다. OpenAI의 캐시 입력은 입력 총계 안의 부분값이고, Anthropic은 일반 입력·캐시 생성·캐시 읽기를 합쳐 표시한다. 추론 요약이 없어도 원본 암호화 상태나 서명이 유지되므로, 요약이 없다는 이유만으로 추론 이력이 누락되었다고 판단하지 않는다.

최종 벤치마크로서는 아직 보완할 점이 있다. 현재 50문제는 계획한 300문제의 파일럿이며, 완료 실행에서도 R2~R5 200개 중 141개만 관측됐다. 또한 미실행 v2의 같은 문자형은 직전 금지쌍 위반이 정상 수순에서 불가능하여, 유효한 완결 오답 대부분이 PE가 되는 구조다. 새 수식을 적용할 수는 있지만 이전 규칙에 특유한 오류와 일반적인 목표 오류를 구별하기 어렵다. 전체 문제를 수정할 때는 이전 규칙이 실제로 선택을 구분하는지도 추가로 검증해야 한다.

## 문항 검증

아래 생성 조건은 기본 데이터 기준이다. 별도 난이도 완화 데이터는 해당 버전의 설명과 전용 검증 명령을 따른다.

검토 화면의 **도달 가능한 최종 조합 수**는 한 라운드에서 더 지울 수 없을 때까지 진행하는 방법을 센다. 처음 문자열에서 어느 위치의 글자들을 한 행동으로 함께 지웠는지 기록하고, 그 묶음들이 같으면 행동 순서가 달라도 한 번만 센다. 예를 들어 `AABB`는 `AA`와 `BB` 중 어느 쪽부터 지워도 빈 문자열로 끝나는 한 조합이다. 금지쌍 위반과 목표 길이를 벗어난 결말도 포함한다. **목표 글자 수에 맞는 조합**은 그중 마지막에 남은 글자 수가 목표와 같은 경우다. 최종 문자열별로 묶음 조합 수와 완주 예시를 볼 수 있다.

예를 들어 SG-001 1라운드의 전체 조합은 46가지이며, 최종 문자열은 10종이다. 그중 한 글자를 남기는 12가지 조합은 `B` 10가지, `C` 1가지, `E` 1가지다.

- 각 문자열에서 적어도 3개의 서로 다른 정답 삭제 순서가 있어야 한다.
- 모든 라운드에서 현재 금지쌍을 지키면서 목표에 성공하는 수순이 있고, 금지쌍을 지키고 물리적으로 끝까지 진행해도 다른 길이가 남아 실패하는 수순이 있다.
- 목표 1·2·3에서는 같은 목표 길이에서 남길 수 있는 글자 구성이 적어도 두 종류다. 예를 들어 `AB`와 `AC`는 두 종류로 세고, `AB`, `BA`, `A B`는 한 종류로 센다. 양수 목표별 라운드의 4분의 1 이상은 세 가지 이상의 서로 다른 글자 구성을 남길 수 있다.
- 목표 0에서는 정답이 빈 문자열 하나다. 같은 입력과 금지쌍으로 1~3글자를 남겨 끝나는 합법 수순도 있어야 한다. 목표 1·2·3에서도 지정 목표와 다른 0~3글자 길이로 끝나는 합법 수순을 확인한다. 여기서 끝난 상태는 같은 구간에 지울 묶음이 하나도 없는 상태다.
- 한 결말만 압도적으로 자주 나오는 판도 걸러낸다. 각 상태에서 현재 규칙상 선택할 수 있는 글자 중 하나를 같은 확률로 고르고, 그 글자의 지울 수 있는 묶음 중 하나를 다시 같은 확률로 고른다고 가정한다. 목표 1~3에서는 성공한 경우에 한 글자 구성이 차지하는 비율이 최대 95%여야 한다. 목표 0에서는 무작위로 골라 전부 지우는 확률이 최대 95%여야 한다. 이 기준은 참가자의 실제 응답 확률과 별도로 계산한다.
- 입력 길이만 보고 목표를 구별하기 어렵게 유형·라운드·목표별로 길이를 배분한다. 서로 다른 글자형의 R2~R5에서는 각 목표에 31글자와 32글자를 한 개 이내 차이로 배정한다. 나머지 유형·라운드·목표 조합에는 각각 28~32글자 길이를 모두 사용한다.
- 원래 분리된 묶음이 합쳐진 뒤 삭제되는 행동을 모든 성공 수순에서 최소 4회 요구한다. 그중 원래 한 글자였던 묶음끼리 합쳐져 삭제되는 행동이 최소 2회 필요하다. 공백 라운드에서는 경계를 없애면 실패하는 수순으로 대표 정답에 도달할 수 있어야 한다.
- R2~R5 전환 200개 각각에서, 현재 입력과 목표에 직전 금지쌍을 적용해 완주하는 수순을 탐색한다. 그 수순에서 다른 합법 행동으로 회복할 수 있었던 현재 규칙 위반이 최소 3회이고, 전체 행동의 40% 이상이어야 한다. 이 비율은 문항을 고르는 조건이다. 참가자의 PER은 제출 단위로 별도로 계산한다.

[generate.mjs](scripts/generate.mjs)가 고정 시드로 문제와 정답을 만들고, [grade.py](src/grade.py)가 독립적으로 검사한다.

## 실행

아래 명령은 `SameGame/` 폴더에서 Python 3.11 이상으로 실행한다. 기본 채점기와 사람 평가 서버는 Python 표준 라이브러리를 사용한다.

```sh
python3 -m src.grade --validate
python3 -m src.grade SG-001 1 --group-counts
```

두 번째 명령은 지정한 라운드의 도달 가능한 최종 조합 수, 목표 글자 수에 맞는 조합 수, 최종 답안별 조합 수를 출력한다.

```sh
python3 -m src.evaluate --item SG-001 --report results.json
```

이 명령은 참가자에게 보낼 영어 요청을 표준 출력에 JSON 한 줄로 쓰고, 표준 입력에서 한 줄에 한 응답을 받는다. 다른 프로그램에서 응답을 받아 연결하거나 직접 입력할 수 있다. 참가자에게는 요청과 피드백을 전달한다. 비공개 제출 기록과 PER/MPE는 `--report`에 지정한 파일에 기록한다. 모델이나 사람의 응답을 이미 수집했다면 한 줄에 한 응답을 쓴 파일로 순서대로 재생할 수 있다.

```sh
python3 -m src.evaluate --item SG-001 --responses submissions.jsonl --report results.json
```

`--item`을 생략하면 50문제를 순서대로 진행한다. 최종 문자열 하나의 도달 가능성만 검사하려면 `python3 -m src.grade SG-008 1 --answer 'A A'`를 사용한다. `node scripts/generate.mjs`는 문제와 정답을 재생성한다.

### 모델 평가

`tower-of-hanoi` 브랜치의 모델 ID와 추론 설정을 사용한다. 제공자별 설정 파일에서 모델을 선택한다.

| 설정 파일 | 프로필 | 모델 | 추론 강도 | 라운드당 최대 시도(T) |
|---|---|---|---|---|
| [configs/openai.toml](configs/openai.toml) | `sol` | `gpt-6.1-sol` | `medium` | 10 |
| [configs/anthropic.toml](configs/anthropic.toml) | `opus` | `claude-opus-5-5` | `medium` | 10 |
| [configs/anthropic.toml](configs/anthropic.toml) | `sonnet` | `claude-sonnet-5-5` | `medium` | 10 |

모든 모델의 라운드당 시도 한도는 10회, 연속 정답 기준은 2회, 응답당 최대 25,000토큰, SDK 통신 timeout은 600초다. timeout은 전체 풀이의 제한 시간이 아니며 스트리밍 도중 데이터를 기다리는 시간에도 적용된다. 첫 라운드에도 동일한 시도 한도와 연속 정답 조건을 적용한다. API 키는 실행 터미널의 `OPENAI_API_KEY` 또는 `ANTHROPIC_API_KEY` 환경 변수에서 읽는다.

```sh
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt

python run.py --config configs/openai.toml --profile sol --output runs/sol
python run.py --config configs/anthropic.toml --profile opus --output runs/opus
python run.py --config configs/anthropic.toml --profile sonnet --output runs/sonnet
```

설정을 먼저 확인하려면 다음 명령으로 첫 요청을 출력한다. `--dry-run`은 API 호출과 결과 파일 생성을 수행하지 않는다. `--item SG-001`로 특정 문제를, `--limit 1`로 앞의 한 문제를 선택할 수 있다.

```sh
python run.py --profile sol --limit 1 --dry-run
python run.py --resume runs/sol
```

`--resume`은 해당 실행 폴더에 저장된 T·k를 그대로 사용한다. 변경한 T=10을 적용하려면 새 실행 폴더로 시작한다. `python run.py --profile sol`처럼 `--output`을 생략하면 날짜·시간을 붙인 새 실행 폴더를 자동으로 만든다.

#### 추론 요약을 남기는 진단 실행

OpenAI 실행에서 `--reasoning-summary`를 지정하면 API가 제공하는 사람이 읽을 수 있는 추론 요약을 저장한다. 값을 생략하면 `auto`이며, `off`, `auto`, `concise`, `detailed` 중 선택할 수 있다. 기본값은 `off`다. 모델과 API가 지원하는 요약 수준을 사용하며, 암호화된 추론 원문을 복호화하는 옵션은 아니다. [OpenAI 추론 요약 문서](https://developers.openai.com/api/docs/guides/reasoning#reasoning-summaries)

```sh
python run.py --profile sol --reasoning-summary auto --output runs/sol_summary
```

이 명령은 현재 Sol 설정(T=10, k=2)으로 50문제를 처음부터 실행한다. 앞의 두 문제만 진단하려면 `--limit 2`를 붙인다. 모델 프로필의 TOML 설정에 `reasoning_summary = "auto"`를 추가해 기본값으로 둘 수도 있으며, 명령행 옵션을 우선한다. Anthropic 실행에서는 이 옵션을 `off`로 둔다.

- `reasoning_log.txt`: 시도 순서대로 입력, 목표·규칙, API 추론 요약, 제출 원문, 피드백, 위반 위치를 모은 평가자용 기록.
- `submissions/00001_reasoning_summary.json`: 각 응답의 요약과 상태(`available` 또는 `empty`), 문제·라운드·시도 정보를 담은 구조화 기록.
- 기존 응답·스트림 파일에도 API가 반환한 원본 요약과 암호화된 추론 상태가 함께 보존된다.

요약 텍스트가 없으면 그 사실을 기록하고 원래 응답을 그대로 채점한다. 추가 호출이나 요약 생성으로 빈 내용을 채우지 않는다. 과제 지시문·제출 형식·네 가지 피드백은 그대로 사용하며, 평가자용 진단 정보는 모델에게 전달하지 않는다. 같은 문제 안에서는 요약을 포함한 제공자의 원본 응답 항목과 암호화된 추론 상태를 보존하고, 다음 문제에서 초기화한다.

진단 옵션은 새 실행의 `protocol.json`에 고정된다. 재개할 때는 `python run.py --resume runs/sol_summary`만 사용한다. 기존 실행에 요약 옵션을 중간에 켜려면 새 실행 폴더가 필요하다. 이미 저장된 응답을 재사용하면 요약 기록도 중복 없이 복구된다. 요약은 모델 내부 과정을 모두 보여주는 기록은 아니므로 실제 제출·피드백과 함께 분석한다.

터미널에는 문제·라운드·시도 진행, 이전·현재 규칙, 응답 대기 시간, 피드백, 삭제 순서, 남은 문자열, 토큰 사용량과 MPE가 표시된다. 규칙은 `A → C 연속 삭제 금지`처럼 표시하고, 각 문제의 첫 라운드는 이전 규칙을 `없음 (첫 라운드)`으로 표시한다. 이전 규칙은 같은 문제의 직전 라운드를 기준으로 하며, 이 정보는 평가자용 터미널에만 표시한다. 파이프로 로그를 저장할 때는 고정된 줄로 출력하며 `NO_COLOR=1`로 색상을 끌 수 있다.

`현재 가능 정답`은 현재 입력에서 현재 규칙을 지키면서 목표에 도달할 수 있는 최종 문자열을 모두 표시한다. 같은 최종 문자열로 끝나는 여러 삭제 순서는 한 번만 표시하며, `"A A"`처럼 내부 공백을 보존하고 빈 문자열은 `∅ (빈 문자열)`로 표시한다. 응답을 받으면 `제출한 삭제`와 `제출한 답안`을 별도로 표시한다. 목록에 있는 문자열을 제출해도 실제 삭제 순서가 규칙을 위반하거나 그 문자열로 끝나지 않으면 정답으로 인정하지 않는다. 이 목록은 평가자용 터미널에만 표시되며, 모델 요청과 참가자 화면에는 전달하지 않는다.

각 실행 폴더에는 고정한 문제·설정을 담은 `protocol.json`, 재개 상태인 `checkpoint.json`, 평가 결과인 `report.json`, 제출별 요청·응답·스트림·채점 기록이 저장된다. 보고서는 지속 오류 기준을 명시한 PER/MPE와 복사 응답 진단을 포함한다. 통신 실패는 시도를 소비하지 않으며, `--resume`은 저장된 완료 응답을 먼저 사용한다. 같은 실행 폴더에 대한 동시 실행은 차단한다.

통신 timeout, 연결 끊김, 최종 응답 없는 스트림 종료, 일시적인 서버 오류는 같은 요청으로 최대 10회 자동 재시도한다(최초 요청 포함 최대 11회). 기본 대기는 약 5·10·20초부터 지수적으로 늘어나 최대 약 1,280초이며 작은 무작위 지연을 더하고, 서버가 `Retry-After`를 지정하면 그 시간 이상 기다린다. SDK 내부 재시도는 꺼 두어 재시도가 중복되지 않게 한다. 인증·권한·잔액 문제와 잘못된 요청은 반복하지 않고 종료한다. 사용자의 Ctrl+C도 즉시 중단한다. [OpenAI 공식 오류 복구 지침](https://developers.openai.com/api/docs/guides/error-codes)

재시도 중에는 문제·라운드·시도 번호와 이전 추론 기록을 그대로 유지한다. 미완성 출력은 답안이나 추론 이력에 추가하지 않으며, 완성된 응답 이벤트가 이미 저장됐다면 재호출보다 복구를 우선한다. 재시도 한도를 소진하면 진행 상태를 보존하고 재개 명령을 출력한다. 실패한 생성도 제공자 측에서 처리됐을 수 있으므로 재시도는 추가 API 사용을 발생시킬 수 있다.

이전 180초 설정으로 시작한 실행도 아래처럼 timeout만 바꾸어 이어갈 수 있다. 문제·프롬프트·모델·채점 조건이 담긴 `protocol.json`은 수정하지 않고, 이번 실행에 적용한 통신 설정과 종료 사유는 `run_events.jsonl`, 개별 실패는 `submissions/*_transport_*_error.json`에 기록한다.

```sh
python run.py --resume runs/sol_easy_r1 --timeout 600
```

`--transport-retries 10`, `--retry-delay 5`로 통신 복구 정책을 조정할 수 있다. 이는 풀이 시도 한도 T와 별개다. `--dry-run`은 재개 호환성과 다음 요청을 API 호출 없이 확인한다. 이번 통신 복구 수정 직전 버전은 `configs/resume_compatibility.json`에 등록한 정확한 코드 지문 쌍만 재개를 허용한다. 지시문·피드백·채점 방식이 다른 과거 실행에는 이 예외를 적용하지 않는다.

오류가 발생하면 실행 폴더의 `errors.log`에 읽기 쉬운 국문 기록을 남긴다. 문제 ID·라운드·풀이 시도·통신 횟수, 발생 시각, 오류 종류, 원래 예외명과 원인 예외, HTTP 상태와 API 요청 ID, 수신 이벤트 수와 마지막 이벤트 종류, 재시도 예정 및 복구 결과를 기록한다. 요청 ID와 HTTP 상태는 제공된 경우에만 남긴다. 로컬 코드 오류는 파일·행·함수 위치를 기록하며, 오류 요약에 API 키·요청 본문·추론 내용·로컬 변수는 포함하지 않는다. Ctrl+C와 모델 응답 생성 미완료도 통신 오류와 구분한다.

나중에 최근 오류와 실행 종료 상태를 확인하려면 다음 명령을 사용한다. API를 호출하거나 저장된 실행을 변경하지 않는다.

```sh
python scripts/check_errors.py runs/sol_easy_r1
python scripts/check_errors.py runs/sol_easy_r1 --limit 20
```

`run_events.jsonl`은 시작·재개·오류·통신 성공·채점·완료의 순서를, `submissions/*_transport_*_error.json`은 개별 통신 오류의 상세 정보를 보존한다. 재개 전 오류를 현재 종료 원인으로 단정하지 않는다. 과거 상세 기록이 없거나 프로세스가 기록을 남길 수 없는 방식으로 종료됐다면 원인을 알 수 없다고 표시하며, 경과 시간만으로 timeout을 판정하지 않는다. 오류 기록 보완은 새로 시작하거나 재개한 프로세스부터 적용된다.

같은 문제의 라운드 사이에는 제공자 고유의 추론 상태와 제출·피드백을 이어 보내고, 다음 문제에서 새 대화를 시작한다. OpenAI는 Responses API의 암호화된 reasoning 항목을, Anthropic은 Messages API의 원래 thinking 블록을 보존한다. [OpenAI 문서](https://developers.openai.com/api/docs/guides/reasoning), [Anthropic 문서](https://platform.claude.com/docs/en/build-with-claude/thinking)
